# Threat model

## Protected assets

- Databricks access and refresh tokens
- Workspace and account configuration
- Unity Catalog metadata and governed data
- Jobs, compute, pipelines, serving endpoints, and their associated cost
- User identity, authorization context, and audit records

## Trust boundaries

The MCP client, MCP server, identity provider, Databricks control plane, and any
state or telemetry backend are separate trust boundaries. Input generated by a
model is untrusted even when the human user is authenticated.

## Primary threats and controls

| Threat | Initial control |
|---|---|
| Prompt injection invokes dangerous tools | Read-only default; explicit risk classes |
| Credential disclosure | Unified auth; no credential tool arguments; log redaction policy |
| Confused deputy or token passthrough | Separate inbound and upstream auth in Phase 3 |
| Cross-workspace data leakage | One explicit SDK client context per server in Phase 1 |
| Unbounded output or cost | Page and result limits; future SQL/compute budgets |
| SSRF through configurable hosts | SDK configuration only; future host allowlists |
| Destructive or privileged operations | Not registered in Phase 1; future approval policy |
| Malicious MCP session identifiers | Never use session IDs as authorization context |
| Supply-chain compromise | Locked dependencies, dependency review, CodeQL, SBOM roadmap |

## Known Phase 1 limitation

Streamable HTTP does not yet implement native MCP OAuth. It must remain on a
trusted interface or behind a correctly configured authenticated reverse proxy.
